1. 목적과 적용 범위
본 프로그램은 관세법령정보포털의 
세계HS 개정표
에서 제공하는 모든 개정 버전과 모든 목록 페이지를 수집하여 SQLite 데이터베이스에 적재한다. 설계서의 요구사항에 따라 품목번호와 국문·영문 설명을 포함한 
레코드 본문 전체
를 저장한다. 포털 화면의 버전 선택 값은 `2017-2022`, `2012-2017`, `2007-2012`, `2002-2007`이며, 프로그램의 기본 실행은 네 버전을 모두 대상으로 한다.[1] 실행 프로그램 `world_hs_revision_crawler.py`는 프로젝트 
루트
에 배치한다.
대상 DB에 기존 데이터가 존재할 수 있으므로 기존 테이블을 변경하거나 삭제하지 않는다. 대신 `world_hs_revision` 접두어의 전용 테이블을 생성한다. 수집 원문의 전체 JSON을 함께 보존하므로, 포털이 이후 필드를 추가하더라도 최초 수집 시점의 원문을 확인할 수 있다.
전체 수집 원칙:
 실제 운영 시 `--max-pages` 옵션을 사용하지 않는다. 이 옵션은 연결 검증 전용이며, 기본 실행은 포털이 반환한 전체 건수에서 계산한 마지막 페이지까지 수집한다.
2. 수집 대상과 방식
프로그램은 화면 HTML을 반복 파싱하지 않고, 해당 화면이 브라우저에서 호출하는 공개 목록 API를 사용한다. 요청에는 개정 전·후 연도, 페이지 번호, 페이지당 건수, 빈 품목번호/설명 조건을 전달한다. 응답의 `resultVo` 목록과 `paginationInfo.totalRecordCount`를 검증하고, 첫 페이지의 전체 건수를 기준으로 마지막 페이지를 계산한다.[1]

4. 데이터베이스 설계
4.1 테이블 생성 원칙
모든 테이블은 `CREATE TABLE IF NOT EXISTS`로 생성한다. 따라서 동일 DB를 여러 번 실행해도 기존 테이블은 삭제되거나 변경되지 않는다. 본문 테이블의 자연키는 `개정 전 연도 + 개정 후 연도 + 포털 원본 일련번호`이다. 이 키를 기준으로 UPSERT를 수행하므로, 재실행 시 중복 행이 생기지 않고 포털 수정 내용은 최신 값으로 갱신된다.

6. 무결성 검증과 장애 대응
프로그램은 레코드를 저장하기 전에 다음 조건을 확인한다. HTTP 상태가 성공이어야 한다. JSON 응답에 포털 오류 플래그가 없어야 한다. `resultVo`가 목록이어야 한다. 전체 건수가 정수여야 한다. 각 페이지의 응답 행 수가 전체 건수와 페이지 번호로 계산한 기대 행 수와 동일해야 한다. 수집 중 같은 버전의 전체 건수가 바뀌면 혼합 시점 데이터를 만들지 않도록 실행을 실패 처리한다.

7. 운영 SQL 예시
다음 SQL은 SQLite GUI 도구 또는 SQLite 지원 애플리케이션에서 실행한다.
-- 버전별 누적 적재 건수
SELECT version_pair, COUNT(*) AS row_count
FROM world_hs_revision
GROUP BY version_pair
ORDER BY version_pair DESC;
-- 최근 실행 이력
SELECT run_id, status, started_at, finished_at,
       expected_records, fetched_records, written_records, skipped_pages, error_message
FROM world_hs_revision_crawl_run
ORDER BY started_at DESC
LIMIT 20;
-- 실패 또는 미완료 페이지
SELECT base_version_year || '-' || revised_version_year AS version_pair,
       page_unit, page_index, status, attempt_count, last_error
FROM world_hs_revision_crawl_checkpoint
WHERE status &lt;&gt; 'COMPLETED'
ORDER BY base_version_year DESC, page_index;
8. 테스트와 검증 결과
배포 패키지에는 외부 포털에 연결하지 않는 단위 테스트가 포함되어 있다. 테스트는 스키마 생성, 전체 원문 JSON 보존, UPSERT 중복 방지와 갱신, 재개 체크포인트, 포털 오류 응답 거부, 버전 파서 검증을 수행한다.
python3 -m unittest discover -s tests -v
2026-09-10에 실제 포털을 대상으로 페이지당 100건으로 
기본 네 버전의 전체 페이지
를 연계 검증했다. 포털의 합계 813건과 실제 수신·UPSERT 건수가 모두 813건으로 일치했고, 10개 페이지 체크포인트가 모두 `COMPLETED` 상태인 것을 확인했다. 또한 검증 DB의 813개 행 모두에 포털 개별 응답 JSON 원문이 보존되었다. 별도로 `2017-2022` 첫 페이지 100건을 제한 적재하는 연결·형식 검증도 수행했다.[1]
9. 향후 확장 고려사항
SQLite는 초기 적재와 단일 운영 환경에 적합하다. 향후 MS-SQL로 이전할 경우 `revision_id`는 `IDENTITY`, 설명과 원문 JSON은 `NVARCHAR(MAX)`, 시간 열은 `DATETIME2`, 고유 제약조건은 동일한 복합 UNIQUE 제약조건으로 매핑할 수 있다. 원문 JSON과 정규화 열을 동시에 보존하는 설계는 검색 인덱스, 벡터 검색, 변경 이력 분석을 추가할 때도 재수집 없이 확장할 수 있게 한다.
